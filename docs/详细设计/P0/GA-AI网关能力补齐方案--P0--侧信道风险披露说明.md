## 1. 目的与适用范围

### 1.1 目的

TEE（可信执行环境）在提供硬件级隔离的同时，存在**侧信道**等业界公认的理论攻击面。为**避免过度承诺、统一对外口径、防范法律风险**，特制定本披露说明，明确：

- TEE 能保护什么、不能保护什么；
- 我们已采取哪些缓解措施、处于什么阶段；
- 对外可以怎么说、不可以怎么说；
- 面对客户追问时的标准答复。

### 1.2 适用场景

| 场景 | 使用方式 |

| 安全白皮书 | **§3-§8** 作为"局限性与风险披露"章的直接来源（逐字引用；与《安全白皮书大纲》v1.1 §5 第 10 章一致） |

适用于 GA-AI 网关密态推理能力（TEE 信封加密路径）。生效版本随产品发布同步更新，见 §10。

## 2. 风险定性

### 2.1 核心定性

1. GA-AI 网关的密态 AI 方案基于**业界主流 TEE 技术（Intel TDX）**构建。
2. TEE 提供的是**"增强保护"**而非"绝对安全"。
3. 侧信道攻击是 TEE **已知的、业界公认的**攻击面。
4. 我们已采取业界最佳实践降低侧信道风险，但**不宣称完全免疫**侧信道攻击。
5. 我们**持续跟踪**学术界与工业界最新研究，并及时更新防护措施。

### 2.2 安全的相对性与分层

```
        ▲ 安全性（示意，非量化承诺）
        │
 物理/硬件层 │  依赖 Intel TDX 与平台固件；侧信道/故障注入属此层风险
 ───────────┼────────────────────────────────────────
 系统/运行时 │  TEE 隔离 + 机密计算运行时（规划中）
 ───────────┼────────────────────────────────────────
 协议/密码层 │  信封 AEAD + 签名 + 防重放 + 密钥轮换（已实现）
 ───────────┼────────────────────────────────────────
 应用/内容层 │  双侧内容审查 + 审计链 + 租户隔离（已实现）
        └──────────────────────────────────────────▶
```

> 说明：上图用于说明"安全是多层叠加、逐层降低风险"，**不表示任何单层的绝对安全**；图中"机密计算运行时（规划中）"对应《TEE 威胁模型》**GAP-08**（当前无 `runtimeClassName` 级隔离）。

## 3. 侧信道与相关威胁类别：我们的边界

> 严重度/可能性/风险评级引自《TEE 威胁模型》第 4、8 章，编号可回溯。

### 3.1 时序侧信道（Timing）

| 项 | 内容 |
|---|---|
| 定义 | 通过执行时间差异推断密钥或敏感数据（经典研究：Kocher 时序攻击） |
| 对 GA-AI 的相关性 | 密态推理涉及密码运算（AEAD、ECDH、KDF）与条件分支 |
| 我们的边界 | ① 遵循常数时间优先原则实现关键密码原语；② 命中/未命中路径引入**同分布随机延迟抖动**（缓存侧，见 §4）；③ **Paillier 模幂不保证常数时间**——该组件依赖可信硬件与独占环境部署（如实披露） |
| 风险评级 | 威胁模型 TG-I-09：高严重度 / 低可能性 / 🟡 低 |
| 状态 | 🟡 部分缓解（非全链路常数时间证明） |

### 3.2 缓存侧信道（Cache）

| 项 | 内容 |
|---|---|
| 定义 | 通过缓存命中模式推断敏感数据（如 Prime+Probe、Flush+Reload；Spectre 类微架构攻击） |
| 对 GA-AI 的相关性 | ① 语义缓存命中/未命中存在可观测差异；② 同宿共置下存在微架构侧信道前提 |
| 我们的边界 | ① 缓存命中/未命中延迟**随机抖动**（主方案 §4.2 R10；P0-2 详设 §7.3）；② 高安全租户可**关闭缓存**；③ 微架构攻击（Spectre 类）依赖 TDX 平台的缓解，我们**未在应用层额外实现**防护，仅作披露 |
| 风险评级 | TG-I-08（中/中/🟠 中）；TG-I-10（高/低/🟡 低） |
| 状态 | 🟡 缓存抖动已实现；微架构层披露为边界 |

### 3.3 功耗侧信道（Power）

| 项 | 内容 |
|---|---|
| 定义 | 通过设备功耗变化推断密钥（SPA/DPA） |
| 对 GA-AI 的相关性 | 云/数据中心部署形态下，功耗观测需**物理接触**或特权基础设施访问 |
| 我们的边界 | 不在软件层防护范围；披露为**已知边界**；依赖数据中心物理安全与平台能力 |
| 风险评级 | TG-I-11：高严重度 / 低可能性 / 🟡 低 |
| 状态 | ⚠️ 不承诺（物理层） |

### 3.4 电磁侧信道（EM）

| 项 | 内容 |
|---|---|
| 定义 | 通过电磁辐射推断数据 |
| 对 GA-AI 的相关性 | 与功耗类似，需物理接触或专业设备 |
| 我们的边界 | 同 §3.3，软件层不承诺；需物理接触/专业设备 |
| 风险评级 | TG-I-11（与功耗同编号）：高严重度 / 低可能性 / 🟡 低（**本体未单列电磁条目**，此处随功耗同编号） |
| 状态 | ⚠️ 不承诺（物理层） |

### 3.5 故障注入 / 熔断（Fault Injection）

| 项 | 内容 |
|---|---|
| 定义 | 通过电压/时钟/温度/电磁等异常使硬件产生错误行为，进而绕过安全检查或恢复密钥（如 Plundervolt、VoltPillager 类） |
| 对 GA-AI 的相关性 | 云部署下需特权基础设施或物理接触 |
| 我们的边界 | 主方案 §4.5.2 列为"**部分**覆盖"：**已知风险披露**，防御措施 P2 评估；当前不提供故障注入防护 |
| 风险评级 | **本体未单列编号**；主方案 §4.5.2 归"部分覆盖"（属物理/硬件层风险） |
| 状态 | ⚠️ 仅披露，未防护（P2 评估） |

### 3.6 TEE 固件 / 微码与平台漏洞（Platform）

| 项 | 内容 |
|---|---|
| 定义 | CPU/TEE 硬件、微码、固件自身漏洞（业界历史上如 Foreshadow、SGAxe、ÆPIC Leak、TDXDown、SMASH 等） |
| 对 GA-AI 的相关性 | 属 TEE 信任根之上的风险，应用层无法完全防御 |
| 我们的边界 | ① 依赖 Intel 与云厂商的**微码/固件补丁**；② 我们跟踪相关公告并评估影响；③ **完整防御依赖供应链上游**，如实披露 |
| 风险评级 | TG-I-01/TG-T-01/TG-SC-04：严重/低-中/🟠 中 |
| 状态 | ⚠️ 依赖平台；无独立硬件度量校验（P1 规划，见《TEE 威胁模型》GAP-03） |

### 3.7 输出侧明文出飞地（设计取舍，非严格侧信道）

| 项 | 内容 |
|---|---|
| 定义 | 输出侧 L2 分类器以**侧车**形式运行，被审查文本以**明文**离开飞地（本体 `TG-I-12`，属"信息泄露"类，非严格侧信道） |
| 对 GA-AI 的相关性 | L1（飞地内）始终生效；L2 为**可选**增强，高安全等级可关闭 |
| 我们的边界 | 如实披露：启用 L2 时明文经飞地外传输（建议 TLS + 内网隔离）；**不宣称"数据全程不出飞地"** |
| 风险评级 | TG-I-12：高严重度 / 中可能性 / 🟠 中 |
| 状态 | ⚠️ 设计取舍，如实披露（详见白皮书第 5 章） |

### 3.8 披露边界小结

| 侧信道类别 | 是否软件层防护 | 对外表述要点 |
|---|---|---|
| 时序 | 部分 | 常数时间优先 + 抖动；Paillier 例外如实证 |
| 缓存（语义缓存） | 是 | 随机抖动 + 高安全租户可关闭 |
| 缓存（微架构） | 否 | 依赖 TDX 平台缓解，仅披露 |
| 功耗 | 否 | 物理层，不承诺 |
| 电磁 | 否 | 物理层，不承诺 |
| 故障注入 | 否 | 已知风险披露，P2 评估 |
| 平台固件/微码 | 否 | 依赖上游补丁，仅披露 |
| 输出侧明文（L2 侧车，TG-I-12） | 否（设计取舍） | 如实披露；**不宣称"数据全程不出飞地"** |

## 4. 已实施缓解措施

> 面向客户"你们做了什么"的追问，逐条给出措施与代码级佐证；状态与《TEE 威胁模型》§9 一致。

| 措施 | 说明 | 佐证（可回溯，`文件:符号`） | 状态 |
|---|---|---|---|
| 常数时间密码实现 | 签名校验/令牌比对采用常量时间比较；关键原语遵循无分支原则 | `gateway/auth-service/jwt.go`（`verifyJWT`）、`gateway/attest-verify/verifier.go`（`VerifyQuote`） | ✅ |
| 缓存命中延迟抖动 | 命中/未命中路径同分布随机延迟，外部难以区分 | 主方案 §4.2 R10；P0-2 详设 §7.3（`gateway/tee-infer-service/cacheengine/jitter.go`） | ✅ |

> **不作承诺的措施（如实提示）**：全链路常数时间证明、硬件度量校验（MRTD/RTMR）、故障注入防护、物理层防护——见 §5。

## 5. 明确不承诺范围

GA-AI 网关**不承诺**（且不会在对外材料中暗示）以下内容：

1. **绝对安全 / 不可攻破 / 100% 数据保密**——任何安全技术均不具备绝对性。
2. **完全免疫侧信道攻击**——TEE 侧信道是业界公认理论攻击面。
3. **防侧信道攻击**能力的完整交付——我们"降低风险"，非"消除"。
4. **物理层攻击防护**（功耗/电磁/探针/故障注入），除非部署环境另行提供物理安全措施。
5. **未公开的 CPU/TEE 硬件漏洞免疫**——依赖 Intel/云厂商补丁。
6. **已通过密评或等保**——除非相应资质材料已正式取得（以合同/证书为准；现状见《TEE 威胁模型》§10）。
7. **默认部署即具备机密计算保护**——机密计算需**显式启用 TDX 形态**；mock 形态仅供开发（对应 GAP-01，**已闭环 ✅ 2026-10-05**：生产形态拒绝 mock）。
8. **对客户自身配置错误、密钥外泄、越权使用导致的风险**负责——见 §8 责任边界。
9. **数据留存/删除权的完整保证**——留存期与删除机制随合规口径推进（现状见白皮书第 5.5 / 9.4；本体 `TG-R-04` / RSK-10）。

## 6. 对外标准披露表述

> **以下文案为对外唯一标准表述，引用时须逐字使用**（可按语种/篇幅择用，不得增删安全承诺）。

### 6.1 标准版（白皮书/官网/技术文档，中文）

> GA-AI 网关密态 AI 方案基于可信执行环境（TEE）技术，在常规软件攻击面之上提供了额外的硬件级保护。我们已实施包括常数时间密码实现、缓存延迟抖动、严格的输入验证与边界检查、飞地降级 fail-closed、密钥分级轮换与审计链完整性校验等在内的多项业界最佳实践，以降低侧信道等攻击的风险。然而，如同所有安全技术一样，TEE 并非绝对安全——侧信道攻击、故障注入以及 TEE 硬件/固件漏洞是机密计算领域公认的理论攻击面。我们持续跟踪学术界与工业界的最新研究，并及时更新防护措施。客户应根据自身安全需求，综合评估本方案的适用性。

### 6.2 极简版（宣传页/对话，中文）

> 我们基于 Intel TDX 提供机密计算级的增强保护：数据在可信飞地内解密与推理，配合信封加密、国密路径与双侧内容安全。同时我们如实说明：TEE 并非绝对安全，侧信道等属业界公认理论攻击面，我们通过多项最佳实践持续降低风险。

### 6.3 英文版（出海/国际客户，供参考）

> The GA-AI Gateway's confidential AI solution is built on Trusted Execution Environment (TEE) technology, providing hardware-level protection on top of the conventional software attack surface. We implement industry best practices—including constant-time cryptographic primitives, cache latency jitter, strict input validation and bounds checking, fail-closed enclave degradation, hierarchical key rotation, and tamper-evident audit chains—to mitigate risks such as side-channel attacks. However, as with any security technology, TEE is not absolutely secure: side-channel attacks, fault injection, and TEE hardware/firmware vulnerabilities are widely recognized theoretical attack surfaces in confidential computing. We continuously track the latest research and update our protections accordingly. Customers should evaluate the suitability of this solution based on their own security requirements.

### 6.4 客户安全团队技术版（尽调/评审场景）

## 7. 禁止与避免表述清单

### 7.1 绝对禁止（出现即须整改）

| ❌ 禁止表述 | 理由 |
|---|---|
| 绝对安全 / 万无一失 | 违反 §2 定性，构成过度承诺 |
| 不可攻破 / 无法破解 | 同上 |
| 防侧信道攻击 / 完全防护侧信道 | 最高发红线；应改为"降低侧信道风险" |
| 100% 数据保密 / 数据绝对不外泄 | 违反 §5.1 |
| 宿主完全无法访问 / 完全隔离 | 应限定为"宿主无法直接读取飞地内存（TDX 正常工作时）" |
| 已通过密评 / 已获等保三级 | 未取得证书前禁用 |
| 已实现完整远程证明 | 应说"已实现飞地证明机制，完整硬件证明链在 P1 接入" |

### 7.2 应避免（易被误读）

| 表述 | 建议 |
|---|---|
| "军事级/银行级加密" | 无标准定义，避免；改用具体算法（AES-256-GCM / SM4-GCM） |
| "零信任" | 与 TEE 场景不直接对应，避免滥用 |
| "硬件级安全"（单独使用） | 须补充"增强保护，非绝对"限定 |
| "免疫 Spectre" | 依赖平台缓解，我方不单独承诺 |
| "密态 = 全程不可见" | 需说明管理面脱敏审计/计量元数据出飞地 |

### 7.3 强制限定词

凡宣称 TEE 安全能力，须同时出现下列限定之一：
- "提供**增强**保护，而非绝对安全"
- "**降低**风险"（而非"消除/防护"）
- "在 TDX 正常工作前提下"
- "**已实现**措施"与"**规划中**措施"须分开表述

## 8. 客户沟通 Q&A

| # | 客户追问 | 标准答复要点（可展开，不可加强） |
|---|---|---|
| **Q1** | "TEE 是不是绝对安全？" | 不是。TEE 提供增强保护，侧信道等为公认理论攻击面。我们通过多项最佳实践降低风险，并持续跟踪最新研究。（引 §6.1） |
| **Q2** | "能防 Spectre 吗？" | 我们的应用层不单独承诺微架构攻击防护，该层依赖 TDX 平台缓解；我们如实披露并跟踪平台补丁。（引 §3.2） |
| **Q3** | "侧信道你们怎么防的？" | 常数时间实现、缓存延迟抖动、高安全租户可关闭缓存、减少飞地驻留与密钥轮换；**Paillier 模幂不保证常数时间**，依赖可信硬件与独占部署。（引 §4） |
| **Q4** | "宿主管理员能不能看到明文？" | 在 TDX 正常工作前提下，宿主无法直接读取飞地内存；但宿主可观测资源用量与时序，这正是我们做侧信道缓解的原因。（引 §3.1/§3.2） |
| **Q5** | "你们有远程证明吗？" | 已实现飞地证明机制（Quote 绑定 nonce 与公钥，客户端校验）；**完整的硬件证明链（Intel DCAP/PCK）与度量校验列入 P1 路线**，当前状态以最新威胁模型为准。（引 §5 第 6 项） |
| **Q6** | "默认部署就是密态的吗？" | 机密计算需**显式启用 TDX 形态**；默认/mock 形态仅供开发，不作为安全承诺。生产部署校验正在加固中（P0 项）。（引 §5 第 7 项） |
| **Q7** | "有等保/密评吗？" | 我们提供国密路径与合规规划；资质状态以实际取得的证书/材料为准，未取得前不作"已通过"表述。（引 §5 第 6 项、§9） |
| **Q8** | "出了安全事故谁负责？" | 我们提供能力范围内的产品安全与响应支持；客户侧配置、密钥保管、越权使用等不在承诺范围。责任以合同约定为准。（引 §5 第 8 项） |
| **Q9** | "有没有第三方审计？" | 渗透测试与第三方审计列入 P1/P2 路线（M5-M9），当前提供内部威胁模型与能力-证据索引供独立验证。 |
| **Q10** | "能不能给一份书面安全边界说明？" | 可以提供本《侧信道风险披露说明》全文（对外版）。 |
