## 4. 问题清单

| ID | 维度 | 角色 | 严重度 | 问题描述 | 影响范围 | 改进建议 |
|---|---|---|---|---|---|---|
| **Q2-01** | 安全隐患 / 逻辑漏洞 | 架构师 / 安全 / 后端 | **P1** | 代理模式下租户身份强制注入缺失。现有 `usage.go handleUsage`（L111-117）与 `sec_center.go handleTeeAudit`（L155-160）均**透传客户端 `tenant` 查询参数**到 tee-infer。本体 §6.4 称「不允许透传客户端 tenant」，但未明确改造方式：是 `requireTenantScope` 校验相等后放行，还是**强制替换**为令牌 tenant？若仅校验相等，攻击者传入空 tenant 或不传 tenant 时，tee-infer 端可能返回全量数据（取决于 tee-infer 侧实现）；且 admin 令牌（空 tenant）调用租户端点时行为不确定 | 租户数据隔离（V-6）、用量/审计跨租户泄露 | 明确 **C-15**：租户侧代理端点**强制以令牌 tenant 替换请求参数**（非仅校验相等），从根本上消除参数篡改风险；admin 超管访问租户端点时须显式传入 `?tenant=` 且落审计留痕 |
| **Q2-02** | 架构设计缺陷 / 安全隐患 | 架构师 / 安全 | **P1** | 双中间件路由隔离策略不明确。既有 `authMiddleware`（管理面三角色）与新增 `TenantAuthMiddleware`（租户面）同在 `:19095`  listener 上，路径前缀均为 `/v1/adminext/`（租户子路径 `/tenant/`）。若某端点挂错中间件（如内部端点误挂 TenantAuthMiddleware 或租户端点误挂 authMiddleware），将直接导致越权。本体仅在 §6.1 区分了前缀，但未明确路由注册的**强制隔离机制**与代码门禁 | 全量越权风险、实现期回归 | 明确 **C-16**：租户端点统一走 `/v1/adminext/tenant/` 前缀，由 `TenantAuthMiddleware` 在路由层**整体包裹**（mux 子树挂载），禁止单端点零散挂接；既有内部端点保持 `authMiddleware`，两类端点注册函数分离、代码评审门禁 |
| **Q2-03** | 逻辑漏洞 / 架构设计缺陷 | 后端 / 架构师 | **P1** | tenant store 与 billing store 双写一致性无保障。注册验证通过后，须写两个独立 SQLite（tenant store 置 `active` + billing store 写 subscription + 配额下发）。本体 §3.2 step2 仅描述了配额未确认时的 `quota_pending` 状态，**未覆盖以下失败路径**：(1) tenant store 写成功但 billing subscription 写入失败；(2) subscription 写入成功但配额下发失败；(3) 以上各步的回滚/补偿机制。各失败路径下租户处于什么状态、是否能登录、如何自愈，均未定义 | 注册流程可靠性、租户状态机一致性、数据不一致排障 | 补充注册状态机（`pending → verifying → subscription_pending → quota_pending → active`），定义每步失败的回退动作与告警；明确人工干预 SOP 与补偿脚本 |
| **Q2-04** | 安全隐患 | 安全 / 前端 | **P2** | CSRF 防护完全缺失。租户侧写操作（创建 Key、修改策略、套餐升级等）经 Console 会话 cookie 认证（`admext1.*`），本体未提及任何 CSRF 防护机制。若 cookie 未设 `SameSite=Strict` 且无 CSRF token，攻击者可构造恶意页面诱导已登录租户执行写操作（如创建 API Key 并转发到攻击者邮箱） | 租户侧所有写操作安全、API Key 被盗用 | 补充 **C-17**：租户侧写操作启用 CSRF 防护（双提交 cookie 或 token 模式）；Console 会话 cookie 设置 `SameSite=Strict` + `HttpOnly` + `Secure`；注册/登录页增加验证码防自动化提交 |
| **Q2-05** | 逻辑漏洞 / 安全隐患 | 后端 / 安全 | **P2** | 密码重置流程不完整。§6.2 仅定义了 `POST /v1/tenant/password-reset`（发重置邮件），**缺少重置确认端点**（如 `POST /v1/tenant/password-reset/confirm`）。只有发信一步而无落地一步，功能不闭环；且发信端点「始终返回 202」的防枚举策略与实际重置效果脱钩 | F1 功能完整性、账号安全 | 补全密码重置流程：新增重置确认端点（校验令牌 + 设置新密码 + 失效令牌 + 全部会话登出 + 落审计）；重置令牌独立于邮箱验证令牌，TTL ≤ 1h，一次性使用 |
| **Q2-06** | 逻辑漏洞 / 架构设计缺陷 | 后端 / 架构师 | **P2** | admin 令牌空 tenant 与 `requireTenantScope` 语义冲突。越权矩阵 §9.1 规定 admin 可跨租户访问租户端点（C-6 客户支持），但 admin 令牌的 `tenant` 字段通常**为空**（内部角色签发不含 tenant，见 `auth.go` L49 omitempty）。`requireTenantScope` 若严格要求令牌 tenant 非空，则 admin 无法访问租户端点；若 admin 例外放行，则 `requireTenantScope` 的「默认拒绝」原则被打破，且 admin 访问时目标 tenant 从何而来（URL 参数？）需明确定义 | 客户支持（C-6）不可用、或越权风险 | 明确 admin 访问租户端点的语义：须在请求中显式指定目标 `tenant` 参数，`requireTenantScope` 对 admin 角色放行参数指定的 tenant，但**强制落审计**（`actor=admin, target_tenant=...`）；admin 不得在无 tenant 参数时访问租户端点（防止全量枚举） |
| **Q2-07** | 安全隐患 | 安全 / 后端 | **P2** | 邮箱验证令牌安全性未定义。本体仅提及「验证令牌（哈希存储）」与「TTL 24h」，未定义：(1) 令牌长度与生成方式（是否密码学安全随机数）；(2) 哈希算法与是否加盐（SHA-256 + salt？）；(3) 一次性使用 vs 可重复使用；(4) 令牌与邮箱的绑定校验（防止令牌交叉使用）。定义不完整易导致暴力破解、令牌重放、跨账号劫持 | 账号劫持、注册滥用 | 补充验证令牌安全规范：32 字节 CSPRNG、SHA-256 哈希存储（带全局 salt）、一次性使用（验证后即失效）、与邮箱绑定校验、TTL 24h、失败计数防爆破 |
| **Q2-08** | 可扩展性问题 / 性能瓶颈 | 运维 / 后端 | **P2** | SQLite tenant store 多副本部署写冲突。本体 §5.1 仅在「限流/风控」处提及多副本问题，**未覆盖存储层**。tenant store 为独立 SQLite 文件，若 gateway-admin-service 多副本部署，SQLite 不支持多写者（写操作串行化且易 `SQLITE_BUSY`）。租户注册、Key 创建、策略更新等写操作在多副本下会出现竞争与失败 | 水平扩展能力、写操作可靠性 | 明确 **C-18**：管理面单副本部署（与限流部署约束一致），或在 §10.2 标注 tenant store 多副本限制；P2 规划迁移到 PostgreSQL 或共享存储方案 |

## 6. 本轮深度发现总结

### 6.1 整改类（与第 1 轮关联）

1. **C-13 延伸**：第 1 轮发现了「tenant_user 不入全局白名单」，本轮深入到「代理层参数注入」——即使角色隔离做对了，代理模式下的透传参数仍是越权通道。
2. **C-14 延伸**：第 1 轮发现了「Console 会话层兜底 admin」，本轮延伸到「admin 访问租户端点时的 tenant 来源」——超管接管路径本身也需要明确的身份模型。
3. **503 fail-closed 延伸**：第 1 轮补充了若干 503 语义，本轮发现验收层缺少验证手段——语义有了但测不出来，等于没保障。

### 6.2 新发现类（第 1 轮未触及）

1. **双中间件路由隔离**：这是实现期高风险点，两个鉴权体系在同一进程中并存，需要架构级的隔离门禁。
2. **双 store 写一致性**：两个独立 SQLite 的分布式事务问题，是注册流程可靠性的核心隐患。
3. **CSRF 防护**：第 1 轮完全未提及前端安全，本轮补齐了 Web 安全基础项。
4. **密码重置残缺**：功能不闭环，属于设计遗漏。
5. **SQLite 多副本写冲突**：与限流问题同源但更严重——限流只是绕过，存储是数据损坏。

### 6.3 需跨文档对齐项

- 与 **P1-3（等保三权分立）**：新增 `tenant_user` 角色不影响三权分立模型（三权分立仅针对管理面内部角色），但需在 P1-3 文档中补充说明。
- 与 **P1-5（国密）**：租户 API Key 的对外签发算法需要与国密方案对齐（Q2-18）。
- 与 **P1-7（审计）**：审计动作清单（附录 D）应与 P1-7 的审计字段规范保持一致。
